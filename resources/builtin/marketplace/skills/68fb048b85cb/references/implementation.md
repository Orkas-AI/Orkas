# 实现与快速反馈

用于实际写代码、修改现有行为或完成研发计划中的编码任务。先完成仓库勘察；多文件、跨模块或不可逆变更先完成决策/计划阶段，再进入编辑阶段。

## 核心循环

1. **锁定切片**：重述当前目标、非目标、不变量和该切片对应的验收证据。
2. **建立基线**：运行最窄的现有测试、复现或静态检查；区分已有失败和新失败。
3. **先读后改**：读取目标定义、直接调用者、同类实现和对应测试，不从孤立文件猜架构。
4. **选择证据路径**：行为稳定且已有测试基础设施时优先 red-green；否则先确定类型、lint、build、局部运行、日志、浏览器或截图等最强替代证据。
5. **最小实现**：一次修改一个可解释切片，不夹带重命名、格式化、抽象升级或无关修复。
6. **立即反馈**：每个切片后先跑便宜且聚焦的语法/类型/lint/单测，再继续扩大修改。
7. **复查调用面**：重新检查受影响调用者、接口、序列化/数据边界和测试，避免半完成迁移。
8. **检查 diff**：确认只有预期文件和行为发生变化，再进入更广验证。

## TDD 使用条件

适合 TDD：目标行为明确、项目已有可运行测试路径、失败能稳定复现。

1. 写一个表达目标行为的聚焦测试。
2. 确认它因预期缺陷失败，而非环境或测试本身错误。
3. 用最小实现使其通过。
4. 必要时整理，并持续保持测试通过。

不要为了“看见红色”而破坏生产代码，也不要给原本没有测试体系的项目强塞新框架。

## 编辑纪律

- 保留用户已有改动；有重叠时先理解并围绕它工作。
- 遵循最近的仓库规则、命名、错误处理、i18n、生成与缓存失效约定。
- 新依赖必须先确认现有依赖不能满足，并进入 change-safety 审查。
- 不在未授权范围内修改 lockfile、迁移、认证、支付、远程服务、CI 权限或发布配置。
- 失败时保留第一条有因果意义的错误，不让后续噪音替代根因。
