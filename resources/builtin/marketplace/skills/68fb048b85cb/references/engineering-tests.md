# 工程测试与验收证据

用于实际编写和运行工程验证。产品级 Given/When/Then 描述“用户应观察到什么”；本 reference 负责决定“用什么可重复证据证明它”。

## 1. 建立验收—证据矩阵

```markdown
| Acceptance / invariant | Evidence type | Exact check | Result | Confidence / gap |
|---|---|---|---|---|
| | unit / integration / contract / E2E / build / lint / type / UI / trace | | verified / static / failed / unverified | |
```

每个需求项至少映射一个证据。一个测试可以覆盖多项，但必须说明映射；没有证据的项不能混进完成结论。

## 2. 选择最小充分测试层

- **静态/契约检查**：格式、schema、资源引用、命令和不变量；快速且确定，但不能代替运行行为。
- **单元测试**：纯逻辑、边界和错误分支；优先靠近缺陷。
- **集成/契约测试**：模块、存储、API、序列化、迁移和外部 adapter 边界。
- **E2E/烟雾测试**：关键用户路径和跨层集成；数量少，覆盖最高风险路径。
- **UI/视觉检查**：真实渲染、交互、空/错/加载态、响应式和可访问性；能运行时检查截图或浏览器结果。
- **性能/原生 trace**：固定场景、环境和采集窗口，对比前后分布或热点；单次样本只作低置信线索。

优先运行能最快定位错误的窄层，再按变更半径扩大。不要仅因为完整套件存在就跳过聚焦测试，也不要只跑聚焦测试就宣称跨系统安全。

## 3. 执行与失败处理

1. 记录精确命令、工作目录、关键环境条件、退出码和摘要。
2. 行为变化适合 red-green 时，先证明测试因预期原因失败。
3. 失败后读取第一条有效错误并进入调试，不盲目重复执行。
4. flaky 结果要记录每次运行和差异；不能挑一次绿色结果当作稳定通过。
5. 因缺依赖、凭据、服务、设备或时间无法运行时，报告阻塞并降级为最强替代证据。
6. 预先存在的失败单独列出，说明是否与当前改动相关；不修无关问题。

## 4. 分层交付门

- 小范围纯逻辑：聚焦测试 + 受影响静态检查 + diff 复核。
- 跨模块/API/数据：上述检查 + 集成/契约 + 相关更广套件。
- 用户界面：上述检查 + 可运行的 UI/截图/交互观察。
- 数据迁移、安全、支付、认证、发布：上述检查 + 失败路径、兼容/回滚和独立复核；没有这些证据不宣称生产就绪。
