# 提交前复核与完成验证

用于声明完成、修复、可交付、测试通过或生产就绪之前。把这一阶段视为独立的 review-on-submit：从需求、完整 diff 和新鲜输出重新判断，不以实现者的叙述为证据。

## 1. 完整 diff 复核

检查所有改变和未跟踪交付文件：

- **范围**：每个改动是否服务当前目标；是否混入格式噪音、调试文件、缓存或无关修复。
- **一致性**：调用者、类型、接口、配置、i18n、生成物、测试和文档是否同步。
- **行为**：happy path、边界、空态、错误态、恢复、幂等和并发是否符合要求或明确不适用。
- **安全**：认证/授权、输入、路径/命令、secret、日志、依赖和最小权限。
- **演进**：兼容、数据迁移、混合版本、可观测性、发布与回滚。
- **用户工作**：已有修改是否保留，是否有被覆盖、重排或误归因的内容。

Review-only 任务到此为止：不修改文件，按优先级报告发现、文件/行证据、影响和修复建议；没有发现时说明仍存在的验证缺口。

## 2. 验收—证据复核

逐项检查 engineering-tests 矩阵：

1. 每项需求/不变量是否有对应证据。
2. 命令是否真的在本轮运行，输出和退出码是否被读取。
3. 每条证据是否晚于最后一次可能影响该验收项的修改；更早的证据已失效，不能沿用。
4. 测试是否验证目标行为，而非仅验证实现细节或 mock 自身。
5. 聚焦检查是否足够；变更半径大时是否运行相关更广检查。
6. 失败、flaky、跳过和未运行是否仍清晰可见。

“测试通过”“构建成功”“bug 修复”“UI 可用”“性能改善”分别需要对应的新鲜测试、构建、原始复现、渲染/交互或同场景性能证据。

## 3. 处理发现并重新验证

- 可在范围内安全修复的发现：做最小修复，在最后一次相关修改后重新运行受影响聚焦检查并读取新输出，再次审阅 diff。
- 暴露新产品决策、外部权限或显著范围扩张：停止并请求方向。
- 只剩无法运行的检查：使用最强静态证据，但将结论降级为未验证，写明阻塞和用户可执行命令。
- 不为获得绿色结果而放宽断言、禁用检查、吞异常或无限重试。

## 4. 交付格式

```markdown
## Delivered
- Scope:
- Key decisions:
- Files / modules changed:

## Acceptance evidence
| Requirement | Command / observation | Result | Status |
|---|---|---|---|

## Review findings resolved
-

## Remaining risk
- Pre-existing failures:
- Unverified paths / blockers:
- Compatibility / migration / rollback:
- Next useful step:
```

完成结论只能覆盖矩阵中“已验证”的范围；静态支持、未验证和失败项不能被总括句抹去。
